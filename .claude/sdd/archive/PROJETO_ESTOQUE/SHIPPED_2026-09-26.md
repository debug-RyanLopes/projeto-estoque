## Summary

Sistema web local de controle de estoque para uso pessoal/single-user: cadastro de produtos (nome, SKU único, preço de compra, preço de venda, estoque mínimo), registro de movimentações de entrada/saída com bloqueio de saída sem estoque suficiente, e alerta visual quando um produto cai no ou abaixo do estoque mínimo. Construído com FastAPI + Jinja2 (server-rendered, sem JavaScript) + SQLite, sem autenticação — decisão explícita para um caso de uso de um único usuário local. Entregue com suíte de testes automatizados cobrindo os 5 acceptance tests definidos na fase de requisitos.

## Lessons Learned

### Process

- Pular a fase de `/brainstorm` formal (documento escrito) não custou qualidade: o diálogo conversacional + a implementação de um MVP funcionando geraram contexto suficiente para o `/define` extrair requisitos com clarity score 14/15 de primeira. Para features pequenas e de escopo já claro na cabeça do usuário, validar com código funcionando pode substituir o documento de brainstorm sem perda.
- Rodar `/define` e `/design` *depois* de já ter um MVP funcionando (em vez de antes) funcionou bem como forma de formalizar e auditar decisões já tomadas — o Design phase encontrou um gap real (padrão SQLAlchemy desatualizado) que só apareceu porque havia código real para comparar contra o KB, não um design abstrato.

### Technical

- Um KB local desatualizado (`Column()`/`Float` como exemplo hand-authored) quase virou o padrão seguido por engano; o processo de Design comparando o código real contra `.claude/kb/python-frameworks/patterns/sqlalchemy.md` pegou isso antes do Build — vale sempre comparar código novo contra o KB, não só contra "o que já está no arquivo".
- `Numeric` vs `Float` para dinheiro é uma decisão pequena de digitar mas com risco real (erro de arredondamento acumulado); confirmar empiricamente que a mudança de tipo não quebra a renderização Jinja/templates (via `@code-reviewer` rodando o servidor de verdade) deu mais confiança do que uma revisão só estática do código.
- Erros de negócio esperados (SKU duplicado, estoque insuficiente) renderizados como banner HTML via redirect+query-string, em vez de `HTTPException`/JSON, combinam melhor com uma UI 100% server-rendered sem JavaScript — evita expor JSON cru para um usuário navegando por formulários.

### Communication

- As perguntas de brainstorm feitas uma de cada vez (single-user? SQLite? FastAPI? alerta visual só?) resolveram toda a ambiguidade de escopo antes de escrever uma linha de código — quando o usuário pediu para "ver funcionando", não houve necessidade de mais perguntas, só executar.
- Quando o usuário pediu explicitamente para "instalar uma base de dados sobre FastAPI" no meio do brainstorm, tratar isso como uma tarefa em background paralela (em vez de bloquear o diálogo principal) manteve o fluxo de descoberta de requisitos sem interrupção, e o resultado (padrão FastAPI validado) ficou pronto a tempo de ser usado no Design.

### Tools & Libraries

- `fastapi.testclient.TestClient` + `app.dependency_overrides` deu isolamento de teste completo (banco temporário via `tmp_path`) sem precisar de nenhuma biblioteca extra além de `pytest`/`httpx` — zero configuração de mocks.
- Delegar tarefas fortemente acopladas (ex.: `database.py`+`models.py`, ou os 3 arquivos de teste) para um único agente especialista, em vez de uma delegação por arquivo, evitou estados intermediários inconsistentes e permitiu que o próprio agente se autoverificasse (rodar pytest) antes de reportar.

## Recommendations for Future Work

| Area | Recommendation |
|------|-----------------|
| Edição de produtos | Hoje só existe cadastro + exclusão (confirmado como COULD/out-of-scope na DEFINE). Se o usuário sentir falta, é um próximo `/define` incremental pequeno. |
| `datetime.utcnow()` deprecated | Encontrado durante o Build (aviso do Python 3.13/SQLAlchemy), deliberadamente não corrigido por estar fora do escopo do DESIGN atual. Vale um `/iterate` futuro no DESIGN para migrar para `datetime.now(datetime.UTC)`, com atenção a linhas já persistidas com datetime naive. |
| HTMX / atualização parcial de página | Documentado como COULD futuro (Decision 3 da DESIGN) — a arquitetura atual (rotas + redirect) já é compatível, não exigiria redesenho. |
| Lint/type-check | Projeto não tem `ruff`/`mypy` configurado. Se o projeto crescer além deste escopo pessoal, vale configurar ambos antes do próximo build. |
